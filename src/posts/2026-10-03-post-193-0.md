## 為啥需要開機自啟動？

試想：DeepSeek 模型在 Linux 伺服器上跑得好好的，突然斷電或重啟，服務就停了！手動重啟費時易錯，對 7x24 在線應用來說簡直噩夢。Systemd 開機自啟動能讓 DeepSeek 服務重啟後自動後台運行，省去人工干預，大大提升效率和穩定性。

## DeepSeek 本地部署環境準備

搞自啟動前，請確保 DeepSeek 模型已在 Linux 伺服器部署好。通常涉及：

1.  **作業系統：** 主流 Linux 發行版（**我用 Ubuntu 22.04 LTS 測試**）。
2.  **Python 環境：** Python 3.8+，推薦 `venv` 或 `conda` 虛擬環境。
3.  **DeepSeek 模型：** `git clone` 倉庫，`pip install -r requirements.txt` 裝依賴。服務多為 FastAPI/Flask Web 應用，或通過 `ollama` 等跑的 LLM。

本教學以 DeepSeek Coder (如 `deepseek-ai/deepseek-coder-6.7b-instruct`) 的 Python 應用為例，假設由 `run_deepseek_service.py` 腳本啟動本地 API。

## 開機自啟動腳本實戰教學

以下是實現 DeepSeek 服務開機自啟動的詳細步驟。我們用 Systemd，它是 Linux 系統初始化和服務管理的標準。

### 第一步：編寫 DeepSeek 啟動腳本

準備 DeepSeek 服務啟動腳本，負責環境變數、虛擬環境激活和啟動命令。假設項目 `/opt/deepseek_service/`，虛擬環境 `venv`。

創建 `start_deepseek.sh`：

```bash
sudo nano /opt/deepseek_service/start_deepseek.sh
```

貼入以下內容：

```bash
#!/bin/bash

# DeepSeek 服務的根目錄
DEEPSEEK_HOME="/opt/deepseek_service"

# Python 虛擬環境的路徑
# 確保你的虛擬環境是在 $DEEPSEEK_HOME/venv 裡
VENV_PATH="$DEEPSEEK_HOME/venv"

# 進入服務目錄
cd $DEEPSEEK_HOME

# 激活 Python 虛擬環境
source "$VENV_PATH/bin/activate"

# 檢查虛擬環境是否激活成功
if [ "$(basename "$(dirname "$(which python)")")" != "bin" ]; then
    echo "錯誤：未能激活虛擬環境。請檢查路徑。"
    exit 1
fi

# DeepSeek 服務啟動命令
# 這裡假設你用一個 Python 腳本來啟動 DeepSeek 模型服務
# 例如，如果是 FastAPI 應用，你可能會用 'uvicorn main:app --host 0.0.0.0 --port 8000'
# 或者如果直接跑模型，那可能是個自定義的 Python 腳本
# 我們用 nohup 確保它在後台運行，並把輸出重定向到日誌文件
nohup python run_deepseek_service.py > $DEEPSEEK_HOME/deepseek_service.log 2>&1 &

# 停用虛擬環境 (非必須，但這是個好習慣)
deactivate

echo "DeepSeek 服務已嘗試啟動。"
```

保存退出 (`Ctrl+X`, `Y`, `Enter`)，賦予腳本執行權限：

```bash
sudo chmod +x /opt/deepseek_service/start_deepseek.sh
```

### 第二步：配置 Systemd 服務單元

Systemd 服務文件是自啟動核心，定義 DeepSeek 服務啟停、監控。

新建 `deepseek.service` 文件：

```bash
sudo nano /etc/systemd/system/deepseek.service
```

貼入以下內容，記得根據實際情況修改 `User` 和 `Group`：

```ini
[Unit]
Description=DeepSeek AI Service
After=network.target multi-user.target

[Service]
# 執行啟動腳本的用戶。請替換成你自己的用戶名，例如 'your_username'
User=your_username
# 執行啟動腳本的用戶組。通常跟用戶名一樣
Group=your_username

# 服務的工作目錄
WorkingDirectory=/opt/deepseek_service

# 啟動命令。確認路徑正確指向你的啟動腳本
ExecStart=/opt/deepseek_service/start_deepseek.sh

# 服務重啟策略：當服務異常退出時自動重啟
Restart=always
# 重啟前等待時間，單位為秒
RestartSec=10

# 標準輸出重定向到日誌 (可選，但強烈建議用於排查問題)
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

保存退出。通知 Systemd 新服務已配置，啟用並啟動：

```bash
sudo systemctl daemon-reload
sudo systemctl enable deepseek.service
sudo systemctl start deepseek.service
```

### 第三步：驗證服務狀態與日誌

服務啟動後，需確認正常運行且重啟能自動恢復。

檢查服務狀態：

```bash
systemctl status deepseek.service
```

應見 `active (running)`。若 `failed`，多半是腳本或 Systemd 配置問題。

排查問題，查服務日誌：

```bash
journalctl -u deepseek.service -f
```

此命令實時顯示日誌，可見 `start_deepseek.sh` 腳本 `echo` 及 DeepSeek 應用輸出。

最後，重啟伺服器，再檢查服務狀態驗證自啟動：

```bash
sudo reboot
```

重啟後，登錄執行 `systemctl status deepseek.service`。順利的話，DeepSeek 會自動運行。

## 我的實測心得

實測 Systemd 配置，幾點心得分享：`ExecStart` 直接調用腳本最穩妥，複雜邏輯獨立，方便排查。`User` 和 `Group` 配置極其重要，Systemd 用戶需有足夠權限。**我曾因權限不足導致服務啟動失敗，浪費不少時間。**

`Restart=always` 和 `RestartSec=10` 簡直救命稻草！Systemd 自動監控服務，DeepSeek 崩潰則 10 秒後重啟，容錯性拉滿。最後，`journalctl -u deepseek.service -f` 實時追蹤日誌是排查啟動問題黃金法則，判斷服務卡住或正常啟動。

## 常見問題

**Q1：DeepSeek 啟動失敗，`systemctl status` 顯示 `failed`，咋辦？**

*   **A1：** 檢查 `start_deepseek.sh` 執行權限（`chmod +x`）。查看 `journalctl -u deepseek.service -f` 日誌，多數問題（如 Python 錯、路徑錯、虛擬環境激活失敗）都在日誌中。確認 `ExecStart` 路徑正確。

**Q2：服務啟動成功，但 DeepSeek 沒正常運行（API 不響應）？**

*   **A2：** 啟動腳本無問題，可能是 DeepSeek 應用內部故障。再查 `journalctl -u deepseek.service -f`，看 DeepSeek 輸出有無錯誤。確認端口未被防火牆阻擋或與其他應用衝突。

**Q3：用 Conda 虛擬環境，啟動腳本怎麼改？**

*   **A3：** 將 `start_deepseek.sh` 中虛擬環境激活命令 `source "$VENV_PATH/bin/activate"` 替換為 `source "/path/to/your/conda/bin/activate" your_conda_env_name`。替換為實際路徑及環境名。

**Q4：改 DeepSeek 參數（如端口號），需重新配置 Systemd 嗎？**

*   **A4：** 不用。修改 `start_deepseek.sh` 腳本裡的 DeepSeek 啟動命令即可。改後，執行 `sudo systemctl daemon-reload` (若服務文件有改動) 及 `sudo systemctl restart deepseek.service` 使更改生效。
